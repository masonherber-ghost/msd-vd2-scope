## Overview

Build the project sequentially through 6 steps, after a Step 0 preflight (Step 6 is optional). **Never start a new step until the user has confirmed the current step is working.** At the end of each step, stop and present the verification checklist, then wait for confirmation before continuing.

`rules-react-shadcn-tailwind.md` is the source of truth for all implementation details — file structure, naming, configuration, and patterns. This skill defines only the sequence and verification gates. If anything here conflicts with the rules, the rules win — except on component CSS, where `rules-css-bem.md` wins.

### Project name

Every step below writes the project name into generated files. **Ask for it before building** — do not infer it, and never copy a name carried over from the project these config files came from.

Ask in plain text (not `AskUserQuestion`), proposing the containing directory's name as the default:

```
What should this project be called? It's used for:
  - the "name" field in package.json
  - the database file (server/<name>.db)
  - the <title> in index.html

The folder is called "<directory-name>" — press enter to use that, or give me another name.
```

Use **kebab-case** for `package.json` and the database filename; use the user's capitalisation for the `<title>`. Throughout the rest of this skill, `<project-name>` means this value.

Then check the config files for a stale name from a previous project — grep the rules and skills for any other project's name and correct it, or flag it:

```bash
grep -rn "<some-other-project>" .claude/ CLAUDE.md
```

### Git repository

Every confirmed step is committed and pushed (see the section below), so settle this **before** Step 1 rather than discovering it at the first gate.

```bash
git rev-parse --is-inside-work-tree   # is this a repo at all?
git remote -v                         # is there a remote to push to?
git branch --show-current             # which branch?
git rev-parse --abbrev-ref --symbolic-full-name @{u}   # is an upstream set?
```

Handle what you find:

| Finding | Action |
|---|---|
| Not a git repo | Ask whether to run `git init` — do not initialise a repo without being asked |
| Repo, no remote | Ask for the remote URL, or whether to stay local-only. Do not invent a URL or create a remote repo unprompted |
| Remote, no upstream on this branch | Note that the first push will use `git push -u origin <branch>` |
| Uncommitted changes already present | Show them and ask whether to commit them first, or leave them out of the step commits |
| All set | Say so in one line and continue |

Also confirm `.gitignore` exists and covers `node_modules`, `.env`, `dist`, and `*.db` before the first commit — Step 1 creates it, but an inherited repo may already have one that does not.

If the user wants to stay local-only, that is fine: commit after each step and skip the push. Say that is what you are doing.

Finally, confirm before building:
- **AI provider** — this stack uses the Anthropic API (`rules-ai-api.md`). Confirm before Step 6.

## After every confirmed step — commit and push

**As soon as the user confirms a step passes, commit that step's work and push it — before starting the next step.** Each step becomes one reviewable commit, so a broken step can be rolled back on its own.

1. Check what is staged first — `git status --short`. Never commit `.env`, `server/*.db`, `node_modules/`, `dist/`, or `*.tsbuildinfo`. If any appear, fix `.gitignore` before committing.
2. Stage and commit with the step number in the subject:

```bash
git add -A
git commit -m "Step <N>: <what the step built>"
git push
```

3. If the branch has no upstream, set it: `git push -u origin <branch>`.
4. If the push fails (no remote, no auth, rejected non-fast-forward), **report it plainly and carry on** — a failed push is not a reason to block the build. Do not force-push.

Do not commit mid-step, and do not commit a step the user has not confirmed.

## Step 2 — Tailwind CSS v4 + Shadcn/UI Setup

Follow `rules-react-shadcn-tailwind.md` → **Tailwind CSS v4** and **Shadcn/UI**.

Build:
- `src/globals.css` with the four required sections in order: `@import "tailwindcss"`, `@theme {}`, `@variant dark {}`, `@layer base {}`
- All required Shadcn/UI color tokens inside `@theme`
- `components.json` at project root
- Core UI components: Button, Input, Card, Dialog, Badge, Select, Textarea, Label
- Stub layout components (no styling) directly in `src/components/`: `Header.tsx`, `Footer.tsx`, `Sidebar.tsx`
- Theme toggle that applies the `dark` class to `<html>`, persisted to `localStorage` via an inline script in `<head>` before first render

Note: no `tailwind.config.ts` — all configuration lives in `src/globals.css` per the rules.

**Tokens — do not invent values.** `rules-design-tokens.md` is the reference for the token system: the one home (`src/globals.css` `@theme`), the naming contract that drives utility generation, the required Shadcn colour names, and how to verify a token compiled. Read it before writing `globals.css`.

Get the actual values one of two ways — never by making them up:

1. **Copy `src/globals.css` from an existing project** and adjust. Fastest, and keeps the naming right.
2. **Extract from the design system** with `/figma-design-system-css`, which reads the real values out of Figma.

Whichever you use, the token block must include:

- The Shadcn/UI colour names listed in `rules-design-tokens.md`, in `oklch()`
- `--radius-*` and `--spacing-*` scales
- `--breakpoint-sm/md/lg/xl` — **these exact names**, or Tailwind generates no responsive modifiers
- `--content-max-width` for the page column, driving `.app-main-inner--fixed`:

```css
.app-main-inner--fixed { max-width: var(--content-max-width); margin-inline: auto; }
.app-main-inner--fluid { width: 100%; }
```

Default the layout to fixed; let a route opt into fluid (`handle: { fluid: true }` read via `useMatches()`) when it needs full width.

**Verify the tokens compiled** — a dropped `@theme` or `.dark` declaration fails silently in the browser:

```bash
npx vite build
grep -oE "@media\(min-width:[0-9]+px\)" dist/assets/*.css | sort -u
grep -o '\.dark{[^}]*}' dist/assets/*.css | head -c 200
```

An empty result means the declarations were dropped.

**When done, stop and show this checklist:**
```
Step 2 verification:
- [ ] Tailwind utility classes apply correctly (e.g. bg-primary, text-muted-foreground)
- [ ] Dark mode activates when clicking the theme toggle
- [ ] Dark mode preference survives a page refresh
- [ ] A Button and Card from Shadcn render with correct styling

Reply "done" when all pass, or describe any issues.
```
**Wait for confirmation before proceeding.**

## Step 3 — Backend Server & SQLite Setup

**Read `rules-database.md` → "Database setup — from scratch" first.** It is the source of truth for the pragmas, migration runner, lazy prepared statements, file storage, and the Express/async pitfalls. This step only sequences the work and verifies it.

Also follow `rules-react-shadcn-tailwind.md` → **SQLite — better-sqlite3 + Express**.

Build:
- Express server at `server/server.ts` with middleware: cors, helmet, express.json
- `better-sqlite3` database at `server/<project-name>.db`
- Migrations system: run-once SQL files in `server/migrations/`, tracked in a `migrations` table
- Repository pattern: `server/repositories/` — one file per entity, no SQL in route handlers
- Route handlers in `server/routes/`
- Centralized error handling in `server/middleware/error-handler.ts`
- CORS origin read from `CLIENT_URL` env var
- `GET /api/health` endpoint for connectivity checks
- WAL journal mode and `foreign_keys = ON` pragmas; `*.db`, `*.db-wal`, `*.db-shm` all gitignored
- File storage: `server/uploads/` served via `express.static`, gitignored — filenames in the database, never blobs
- Vite proxy: `/api` **and** `/uploads` → Express in `vite.config.ts` (a proxy missing `/uploads` returns `index.html` for images with a 200, which looks like a broken image and logs nothing)
- Backup script at `scripts/backup-db.ts` — copies `server/<project-name>.db` to `server/backups/` with a timestamped filename, prints filename, size, and total backup count (this is what the `/backup-db` skill runs)

For verification, also build a minimal **notes** feature end-to-end:
- Migration: `notes` table (`id`, `text`, `created_at`)
- Repository: `server/repositories/notes-repository.ts` with `getAllNotes()` and `createNote(text)`
- Routes: `GET /api/notes` and `POST /api/notes` in `server/routes/notes.ts`
- Temporary UI in `App.tsx`: a text input + submit button that posts a note, and a list below that shows all notes fetched from the API

The notes UI uses plain `useState` + `fetch` — it will be replaced with TanStack Query hooks in Step 4. The backend code is permanent.

**When done, stop and show this checklist:**
```
Step 3 verification:
- [ ] `npm run server` from root starts without errors
- [ ] `server/<project-name>.db` exists after server starts
- [ ] Open http://localhost:5173 — type a note, submit, and see it appear in the list
- [ ] Restart the server (`npm run server`), refresh the page — the note is still there
- [ ] `npx tsx scripts/backup-db.ts` writes a timestamped copy into `server/backups/`
- [ ] Restarting the server logs "Migrations up to date" (not re-applying them)
- [ ] An invalid request (empty body) returns a 4xx AND the server is still alive afterwards

Reply "done" when all pass, or describe any issues.
```
**Wait for confirmation before proceeding.**

## Step 6 (Optional) — Anthropic API Integration

Follow `rules-ai-api.md` — it is the source of truth for SDK usage, model choice, prompt handling, and error mapping.

Key rules: API key server-side only (never a `VITE_` var); all prompts centralised in `server/prompts.json` with `{{variable}}` placeholders substituted and sanitised at runtime; rate-limit all AI routes; catch provider errors and return user-friendly messages; mock the AI service at the boundary in tests — never call the real API from a test.

Skip this step if the project does not require AI features.

### Before building — make sure there is an API key

Check for the key **before** writing any AI code, so the step ends with a working endpoint rather than a 503:

```bash
ls server/.env 2>/dev/null && grep -c '^ANTHROPIC_API_KEY=.\+' server/.env
git check-ignore -q server/.env && echo "gitignored" || echo "NOT IGNORED — fix .gitignore first"
```

**The key belongs in `server/.env`, never the root `.env`.** The root file is the one Vite reads; a secret there is one careless `VITE_` prefix away from being compiled into public client JavaScript. If you find `ANTHROPIC_API_KEY` in the root `.env`, move it to `server/.env` and say why.

Confirm `server/.env` is gitignored **before** telling the user to paste a real key into it. If it is not, fix `.gitignore` first.

If the file or the key is missing, create the template from the example and prompt the user in plain text (not `AskUserQuestion`):

```bash
cp server/.env.example server/.env
```

Then say:

```
I need an Anthropic API key to finish this step.

1. Go to https://platform.claude.com/settings/workspaces/default/keys
2. Click "Create key", give it a name, and copy the value
   (you can only see it once — copy it before closing the dialog)
3. Open server/.env and paste it after the = on the ANTHROPIC_API_KEY line:

     ANTHROPIC_API_KEY=sk-ant-...

   No quotes, no spaces around the =.

server/.env is gitignored, so the key will not be committed.
Put it in server/.env, not the root .env — the root file is bundled by Vite.

Reply "done" once it's saved and I'll verify the connection.
```

Wait for the user. Never ask them to paste the key into the chat, and never read the key value back out — verify by making a request, not by printing the file.

When they reply, restart the server (dotenv reads the file at boot) and confirm with one real request to the AI endpoint.



Build:
- `@anthropic-ai/sdk` installed; `ANTHROPIC_API_KEY` added to `server/.env.example` as an empty placeholder
- `server/prompts.json` with a placeholder feature entry
- `server/services/anthropic-service.ts` with one service method
- One `/api/ai/` route with `express-rate-limit` applied
- AI endpoint function added to `src/lib/api-client.ts`
- `src/hooks/useAnthropic.ts` wrapping a TanStack Query mutation

**When done, stop and show this checklist:**
```
Step 6 verification:
- [ ] A prompt from prompts.json loads and substitutes variables correctly
- [ ] The /api/ai/ endpoint returns a response from the Anthropic API
- [ ] A missing or invalid API key returns a user-friendly error (not a stack trace)
- [ ] The useOpenAI hook drives the UI — no direct fetch() in components

Reply "done" when all pass, or describe any issues.
```

**Wait for confirmation before proceeding.**

## Rules

- **Run Step 0 first.** Never start Step 1 before the preflight passes.
- **Work sequentially.** Do not skip or combine steps.
- **Commit and push after every confirmed step**, before starting the next one.
- **Stop and wait** for confirmation at every checklist before starting the next step.
- If the user reports a failure, diagnose and fix before re-presenting the checklist.
- Do not add features, abstractions, or dependencies beyond what each step describes.
